# Flowcode

### A programming language designed for automation — and for AI.

What if an AI could build an entire software system in one session?

Not by generating thousands of lines of framework code.
Not by creating dozens of files and hoping everything connects.

But by writing a program that looks much more like the **intent of the software itself**.

That's the idea behind Flowcode.

---

## See it in 30 seconds

Suppose you tell an AI:

> When a user submits an image, analyze it with AI.
> If the image is safe, store it and email the user.
> If it isn't safe, ask a human to review it.
> If they approve it, store it anyway. Otherwise reject it.

A conventional implementation might require an API server, background worker, database, queue, AI SDK, email library, moderation logic, retry handling, and a bunch of glue code.

In Flowcode, the program can look like this:

```flowcode
workflow: ImageModeration

trigger:
  webhook "/images"

step image:
  http.get
  url = payload.url

step analysis:
  ai.classify
  input = image
  categories = ["safe", "unsafe"]

match analysis.result

  case "safe":
    storage.put
    input = image

    email.send
    template = "approved"

  case "unsafe":

    step review:
      form.render
      form_id = "moderation_review"
      data = image

    step decision:
      await form.submit
      form_id = "moderation_review"

    match decision.status

      case "approved":
        storage.put
        input = image

        email.send
        template = "approved"

      case "rejected":
        email.send
        template = "rejected"
```

That's the point.

**The workflow is the program.**

There is no framework to learn, no queue API to wire together, and no asynchronous state machine to implement.

The runtime handles those things.

---

# And it's actually executable

Flowcode isn't a diagramming language or a prompt format.

The source is compiled into bytecode and executed by the Flowcode VM.

```bash
git clone https://github.com/tayyebi/flowcode
cd flowcode

make
```

Run a workflow:

```bash
./flowcode run examples/hello.fc
```

Compile it:

```bash
./flowcode compile examples/hello.fc
```

Inspect the generated bytecode:

```bash
./flowcode inspect examples/hello.fcb
```

The exact commands may evolve while the project is experimental, but the important distinction is:

> **Flowcode programs execute.**

# Try a tiny program

Start with something deliberately boring:

```flowcode
workflow: Hello

step message:
  print "Hello from Flowcode!"
```

Run it:

```bash
flowcode run hello.fc
```

Output:

```text
Hello from Flowcode!
```

Now add data:

```flowcode
workflow: Hello

step greeting:
  set message = "Hello"

step name:
  set name = "world"

step result:
  print "{{greeting.message}}, {{name}}!"
```

The same basic model scales to external systems.

# Call an API

```flowcode
workflow: Weather

trigger:
  manual

step weather:
  http.get
  url = "https://api.example.com/weather"

step output:
  print weather
```

The HTTP operation is a language-level capability.

The workflow doesn't need to know how sockets, HTTP clients, serialization, connection pooling or retries are implemented.

The runtime/plugin does.

---

# Use an AI model

AI can be another operation in the program:

```flowcode
workflow: DocumentExtraction

trigger:
  webhook "/documents"

step document:
  http.get
  url = payload.url

step customer:
  ai.extract
  model = "vision"
  input = document
  schema = Customer

step output:
  print customer
```

The important part is that **AI isn't special infrastructure anymore**.

It's simply something a program can call.

---

# Wait for a human

Automation doesn't always mean removing humans.

Sometimes the correct program is:

```flowcode
workflow: Approval

trigger:
  webhook "/request"

step form:
  form.render
  form_id = "approval"
  data = payload

step decision:
  await form.submit
  form_id = "approval"

match decision.status

  case "approved":
    print "Approved"

  case "rejected":
    print "Rejected"
```

The workflow can pause.

The process can continue later.

The human interaction is part of the program rather than an external system bolted onto it.

---

# Run things in parallel

Suppose an order needs to update the CRM and send an email.

```flowcode
workflow: OrderCompleted

trigger:
  webhook "/orders/completed"

parallel:

  step crm:
    crm.create
    data = payload

  step email:
    email.send
    template = "order-confirmation"
    data = payload
```

The intent is explicit:

> **These two things can happen concurrently.**

The runtime handles scheduling.

---

# Loop over data

```flowcode
workflow: ProcessDocuments

trigger:
  manual

loop document in payload.documents

  step extracted:
    ai.extract
    input = document

  step save:
    storage.put
    input = extracted
```

Again, the program describes the operation rather than its implementation machinery.

# Why this matters for AI

Now imagine giving an LLM this specification:

> Build a customer onboarding system.
>
> * Receive applications through an API.
> * Download uploaded identity documents.
> * Extract the customer's information with AI.
> * Validate the extracted data.
> * If the application is suspicious, send it to a human reviewer.
> * If approved, create the customer in the CRM.
> * Send a welcome email.
> * Keep the process resumable if the human doesn't respond immediately.

A conventional coding agent has to decide:

* Which framework?
* Which HTTP library?
* Which queue?
* Which database?
* How should jobs be serialized?
* How should retries work?
* How do we persist workflow state?
* How do we resume after a process restart?
* How should concurrency work?
* How should integrations be abstracted?
* Where does the human approval state live?

With Flowcode, most of those decisions are already encoded in the language/runtime.

The agent can focus on:

```text
receive
→ fetch
→ extract
→ validate
→ review
→ branch
→ create
→ notify
```

That is a dramatically smaller problem.

# The idea

Today's programming languages were designed primarily for humans.

They give us enormous expressive power:

```text
classes
functions
modules
generics
inheritance
threads
callbacks
frameworks
packages
configuration
```

That's useful when a human developer incrementally constructs software.

But AI agents have a different problem.

When an LLM builds an application, a large portion of its output is often glue:

* API clients
* configuration
* serialization
* error handling
* orchestration
* state management
* retries
* concurrency
* integration code
* framework boilerplate

The actual intent of the software is often much smaller.

Flowcode explores a different approach:

> **What if the programming language itself represented the things an AI needs to build and operate software?**

Consider this:

```text
receive customer
      ↓
download documents
      ↓

      ↓

      ↓
ask human
      ↓
approved?
   ↙       ↘
 yes       no
  ↓         ↓

  ↓

```

That's already a program.

The traditional implementation is merely one way of realizing it.

Flowcode tries to make that representation executable.

# Automation-friendly programming

Flowcode is not intended to replace Python, Rust, Go, C++, or JavaScript.

It explores a different point in the design space.

Traditional languages are excellent at **computation**.

Flowcode is designed around **orchestration**.

Its primitives correspond to things modern software constantly does:

```text
http.get
http.post

email.send

ai.extract
ai.generate

store.get
store.set

form.render
await form.submit

emit

parallel

loop

match
```

The goal is to make the **automation itself the program**.

# Why Ansible feels so good to AI

There is a reason LLMs tend to perform well when generating configuration and automation languages.

Consider:

```yaml
- name: Install nginx
  apt:
    name: nginx

- name: Start nginx
  systemd:
    name: nginx
    state: started
```

The model isn't inventing arbitrary implementation details.

It expresses:

> install this
> ensure this state

The vocabulary is constrained.

The semantics are explicit.

Flowcode applies the same principle to a broader class of software:

> **Give the AI a small, composable vocabulary for describing what the system should do.**

# AI as a software builder

The long-term experiment is not:

```text
LLM → generate Python faster
```

It is:

```text
Human intent
     ↓
    LLM
     ↓
 Flowcode
     ↓
 Runtime
     ↓
 Real software
```

The LLM becomes a programmer operating at the level of the application's intent.

The runtime becomes responsible for execution.

---

# Why a runtime instead of generated code?

Because generated code is difficult to control.

If an AI generates arbitrary Python, it can potentially:

* import anything
* execute anything
* create arbitrary processes
* modify arbitrary files
* make arbitrary network requests

Flowcode gives the runtime a controlled execution model.

A workflow can say:

```flowcode
http.get
```

without giving the generated program unrestricted access to the machine.

Capabilities can be exposed through plugins.

The runtime knows what operations exist.

The program knows what operations it is allowed to request.

This creates a useful boundary between:

**what the AI wants to happen**

and

**what the execution environment permits.**

---

# Programs that outlive processes

Automation rarely looks like:

```text
start → execute → finish
```

Real automation looks like:

```text
receive request
      ↓
call API
      ↓
wait
      ↓
ask human
      ↓
wait two days
      ↓
receive response
      ↓
continue
      ↓
retry failure
      ↓
finish
```

Flowcode treats this as a normal program.

State can be persisted.

Execution can be resumed.

Human interaction can suspend a workflow.

External events can continue it.

This makes long-running processes a language primitive rather than an application-level invention.

# Under the hood

Flowcode separates the program from its execution.

```text
              .fc source
                  │
                  ▼
              Compiler
                  │
                  ▼
              Bytecode
                  │
                  ▼
                  VM
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
       HTTP       AI      Storage
        │         │         │
        └─────────┼─────────┘
                  ▼
             Real world
```

The compiler produces bytecode.

The VM executes it.

Plugins provide capabilities and integrations.

This means an AI-generated program targets a **known execution model** rather than an arbitrary collection of libraries and frameworks.

# Flowcode is an experiment

Flowcode does not claim to be the final programming language for AI.

It asks a question:

> **If AI becomes the primary author of software, should programming languages continue to be optimized primarily for human authors?**

Flowcode is one possible answer.

The current implementation focuses on automation and orchestration because this is where the idea is easiest to test.

---

# The real benchmark

The most interesting experiment isn't whether Flowcode can express a workflow.

It can.

The interesting question is:

> **Can an AI build larger software systems more reliably in Flowcode than in a conventional programming language?**

For example, give an agent the same specification twice:

### Implementation A

```text
Python + FastAPI + PostgreSQL + Celery + Redis
```

### Implementation B

```text
Flowcode
```

Measure:

* time to first working version
* number of iterations
* number of compilation/runtime errors
* amount of generated code
* number of human interventions
* number of integration mistakes
* ability to modify the system
* ability to recover from failures

If Flowcode wins, the language has demonstrated something meaningful.

If it doesn't, we've learned something equally useful.

# The vision

Imagine saying:

> Build me a service that receives orders, validates payments, detects fraud with an AI model, asks an employee to review suspicious orders, reserves inventory, creates shipments, emails customers, retries failed integrations, and keeps an audit trail.

And the AI produces:

```text
one program
```

rather than:

```text
47 source files
12 configuration files
3 workers
2 queues
8 libraries
4 SDKs
and 2,000 lines of glue
```

That's the direction Flowcode is exploring.

---

# The thesis

> **The next generation of programming languages may not be designed for humans to write software faster.**
>
> **They may be designed for AI to build software more reliably.**

Flowcode is an experiment in what that might look like.

## Status

Flowcode is experimental.

The repository currently includes:

* Flowcode compiler
* bytecode generation
* virtual machine
* workflow scheduler
* persistent state
* branching
* loops
* parallel execution
* asynchronous `await`
* plugin-based integrations
* structured errors
* event emission
* example automation programs

The implementation is evolving.

The thesis is the important part.

**Try giving it a real software specification and see what an AI can build.**
